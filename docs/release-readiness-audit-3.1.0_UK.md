# Звіт аудиту готовності до релізу 3.1.0 (функціональна повнота)

> Мета: проти зобов'язань ROADMAP 3.1.0 перевірити пункт за пунктом, чи функції **справді
> замкнені в цикл і працездатні**, чи є прогалини / напівфабрикати / дефекти.
> Метод: 3 паралельні субагенти за функціональними доменами (тестовий інтелект /
> тривоги·синхронізація / KB·документи) виконали тришарову перевірку проводки (вхід → VM → API →
> контракт бекенду) плюс перевірки замкненого циклу / зворотного зв'язку / крайніх випадків;
> готовність до релізу перевірено окремо.
> Дата: 2026-09-22. Вердикт: **блокувальних для випуску пунктів немає**; 1 підтверджений дефект
> уже виправлено; кілька пунктів рішень щодо вимог — наприкінці.

## 1. Test Intelligence M9 — ✅ придатний до випуску

- **Повний**: вхід зі списку сесій (шлюз backendReady) → список проєктів → деталі з чотирма
  блоками (функціональні точки + юніт-тести + проблеми + виправлення) → AI-чат; усі три шари
  проводки проходять і збігаються з контрактом бекенду поле за полем; підтвердження проблем /
  прив'язка до функціональних точок, apply виправлень (file/patch/branch) / відкат / відхилення,
  попередній перегляд diff, стани збою/порожньо/завантаження — усе на місці.
- **⚠️ Прогалини (неблокувальні, усунуто 2026-09-22)**:
  - Події `intel.gate.blocked`/`fix.suggested`/`fix.applied`/`chat.answer`/`env.ready` парсилися,
    але не мали виходу в сповіщення/UI (парсилися в `Unit`); збій шлюзу показував лише Toast
    «запуск не вдався» без причини → **виправлено**: усі п'ять типів подій тепер створюють
    сповіщення (`showGateBlockedNotification` тощо), а збої `startRun` показують причину бекенду.
  - Після запуску тестового прогону його статус **не оновлювався автоматично** (`intel.run.event`
    не споживався для оновлення списку; потрібне ручне оновлення) → **виправлено**: додано
    глобальний `IntelRunEventBus`; шар push публікує `intel.run.event`, екран деталей проєкту
    підписується та зливає список прогонів у реальному часі за projectId; термінальні стани
    прогонів також оновлюють блоки проблем/виправлень.
  - Невдалий `loadRunResults` **назавжди кешувався як порожній** (захист ідемпотентності робив
    повторну спробу неможливою на цьому екрані) → **виправлено**: збої більше не пишуть порожній
    кеш; набір `runResultsFailed` позначає це, а UI показує «не вдалося завантажити, торкніться
    для повтору».
  - **Підсвітка SECURITY_WARNING — мертвий код**: `recordRunIssues` на бекенді жорстко прописує
    серйозність проблеми `"medium"` і `featureId=0`, тож червоний бейдж «!» у застосунку
    **ніколи не спрацьовує**; справжні знахідки безпеки (`/api/intel/findings`) не мають клієнта.
  - У списку проєктів немає показу «модулів» (`BackendApi.intelModules` — нуль викликачів);
    `anchor` функціональної точки не рендериться.
  - Мертвий код: `intelRunDetail`/`featureRunTest` не мають викликачів (і бекенд дозволяє лише
    scope admin, тож нешкідливо).

## 2. Сповіщення моніторингу серверів — ✅ придатний до випуску

- **Повний**: контракт GET/POST `/api/alerts` збігається; картка керування сервером
  (увімкнення + редагування порогів 0-100 + червона крапка перетинання порогу); push
  `alert.hardware` → сповіщення + запис в історію; локальна історія (SQLite, 7 днів) + 60-с
  узгодження опитуванням із дедуплікацією.
- **⚠️ Прогалини (неблокувальні)**:
  - Рівні серйозності **warning/info не реалізовані** (парсяться, але не використовуються;
    alert/ok мають спільний канал і пріоритет).
  - Історія тривог **не оновлює UI автоматично після запису** (потрібне ручне оновлення).
  - Поріг 0 на бекенді тихо відкатується до 90 (UI показує 90, що не збігається з введеним).
  - Видалення сервера не чистить його історію (автоматичне спливання за 7 днів).
  - Відповіді, відмінні від 2xx, десеріалізуються в порожній знімок (401/500 показують
    «моніторинг вимкнено» замість підказки про збій; узгоджується із загальною схемою проєкту
    без expectSuccess).

## 3. Синхронізація між пристроями — ✅ придатний до випуску (1 формальний дефект виправлено)

- **Повний**: контракт GET/PUT `/api/sync` збігається (key=global, виявлення дрейфу ревізій);
  SyncSettingsScreen має повний набір опцій бекенду (лише https/loopback + обов'язковий токен);
  автосинхронізація WorkManager кожні 15 хвилин; `disconnect()` чистить лише sync-облікові
  дані (виправлення перевірено).
- **❌→✅ виправлено**: обробка 404→null у `syncGetBundle` була зламана (HttpClient без
  expectSuccess ніколи не кидає `ClientRequestException`, тож 404 десеріалізувався в порожній
  Bundle) → **перший запуск синхронізації з новим бекендом завжди давав хибний CONFLICT**.
  Змінено на явне повернення null при `status==404` (`BackendApi.kt:764`), відновивши семантику
  MISSING_UPLOAD на першій синхронізації. `catch (ClientRequestException)` у `read()/write()`
  залишається як захисний код.

## 4. База знань (KB) — ✅ придатний до випуску (1 прогалина в зобов'язаннях потребує рішення)

- **Повний**: подвійний вхід (керування сервером + список сесій, обидва тепер ведуть на
  зареєстрований маршрут `Kb`); список/створення колекцій, список документів, приймання
  тексту/файлів (попередня перевірка розміру + потокова обробка), семантичний пошук (оцінка +
  сніпети); усі три шари проводки проходять, контракт збігається.
- **⚠️ Прогалина в зобов'язаннях**:
  - **Немає UI для видалення колекцій/документів**: `BackendKbApi.deleteCollection/deleteDocument`
    мають нуль викликачів, а ROADMAP уже відзначає «список/створення/видалення колекцій» —
    **потрібне рішення**: додати UI видалення або переформулювати ROADMAP на «керування
    залишається у Web».
    → **Усунено**: UI видалення додано (`KbScreen.kt:219`, `KbCollectionDetailScreen.kt:307`);
    див. §7, пункт 2.
  - Приймання файлів приймає лише `text/*` (`contentBase64` не має викликачів; бекенд
    підтримує PDF/Office через multipart).
  - Невідповідність лімітів розміру: клієнт 5 МіБ проти тіла JSON бекенду 4 МіБ — текст 4–5 МіБ
    отримає відмову 413.
  - Документи KB не можна попередньо переглядати (бекенд не має endpoint завантаження;
    ROADMAP позначає це відкладеним).

## 5. Генерація документів — ✅ придатний до випуску (кнопка перегляду потребує рішення)

- **Повний**: вхід із панелі вводу → діалог генерації (PPT/Word/Excel) → картка повідомлення
  (завантажити/доопрацювати) → перегенерація за інструкцією; контракт збігається, цикл замкнений.
- **⚠️ Дефект (потрібне рішення)**:
  - **Кнопка перегляду завжди дає 401 під час виконання**: WebView у `DocumentPreviewSheet`
    не надсилає заголовків автентифікації, тоді як endpoint завантаження бекенду вимагає
    `X-Web-Session`/`Authorization` (токен застосунку не досягає WebView жодним із них). ROADMAP
    перелічує перегляд як відкладений, але кнопку вже викрито — **потрібне рішення**: сховати
    вхід перегляду або полагодити автентифікацію (впорскнути заголовки).
    → **Усунено**: заголовки автентифікації тепер впорснуються через `shouldInterceptRequest`
    (`DocumentPreviewSheet.kt:166-188`); див. §7, пункт 1.
  - Зарезервовані API (listDocuments/getDocument/deleteDocument) не мають викликачів (нешкідливо).
